# 단일 서버 운영 준비

이 문서는 Linux 서버 한 대, 로컬 Nginx 한 개, 백엔드 프로세스 한 개를 기준으로 한 배포 템플릿입니다. 실제 호스팅·도메인·인증서는 아직 정하지 않았고 외부 배포도 하지 않았습니다. Windows 로컬 개발은 기존 `npm.cmd run dev`를 그대로 사용합니다.

## 구성과 접근 권한

- 외부에는 HTTPS 443과 HTTP 리다이렉트 80만 공개합니다. 백엔드는 `127.0.0.1:3001`에 바인딩하고 외부 3001 접근을 허용하지 않습니다.
- Nginx 문서 루트는 프론트엔드의 `dist`만 지정합니다. 저장소 루트, backend, `.env`, SQLite 파일을 정적 파일 경로에 넣지 않습니다.
- 운영 관리는 SSH 등 서버 인증을 통과한 운영 계정으로 합니다. 공개 관리자 API나 설정 변경 화면은 없습니다. 현재 공개 API는 생성·수정·개인 사용량·최소 health 응답뿐입니다.
- 별도 서비스 계정으로 백엔드를 실행하고 코드에는 읽기 권한, `/var/lib/sebit`에는 쓰기 권한만 줍니다. 서비스 실행 시 `umask 0077`을 적용해 신규 DB·저널 파일을 보호합니다. 기존 파일도 소유자·권한을 확인합니다.
- API 키를 보관한 환경 파일은 저장소와 정적 웹 루트 밖에 두고 서비스 계정만 읽도록 합니다. Nginx 계정에는 읽기 권한을 주지 않습니다. 비밀값을 배포 로그·스크립트 인자·채팅에 출력하지 않습니다.

## 운영 환경값

호스팅에 맞게 다음 값을 환경 파일에 설정합니다. `backend/.env.example`의 나머지 모델·한도 설정도 포함합니다. `NODE_ENV=production`에서는 HTTPS origin, 루프백 바인딩, 명시한 로컬 프록시, 서로 다른 절대 DB 경로가 필수이며 위반하면 서버 시작을 중단합니다.

```dotenv
NODE_ENV=production
HOST=127.0.0.1
PORT=3001
APP_ORIGIN=https://dashboard.example.com
APP_ALLOWED_ORIGINS=
AI_TRUSTED_PROXIES=127.0.0.1
AI_USAGE_DB=/var/lib/sebit/ai-usage.sqlite
AI_TELEMETRY_DB=/var/lib/sebit/ai-events.sqlite
```

`.env`의 실제 키와 모델은 운영자가 별도 설정합니다. DB 경로는 릴리스 디렉터리 밖에 유지해야 코드 교체·롤백 때 한도와 쿠키 서명이 초기화되지 않습니다. 이 검사는 파일 권한이나 방화벽을 자동으로 설정하지 않습니다.

## 프록시 계약

[nginx.conf.example](nginx.conf.example)의 도메인·인증서·경로를 실제 환경으로 교체합니다. 인증서는 별도 발급·갱신 절차를 구성해야 하며, 예시 자체가 인증서를 발급하지는 않습니다.

`AI_TRUSTED_PROXIES`는 정확한 IP만 지원합니다. 기본값은 빈 값이며 로컬 직접 개발에서는 전달 헤더를 무시합니다. 신뢰한 peer일 때만 `X-Forwarded-For`의 단일 IP를 사용합니다. Nginx가 반드시 `$remote_addr`로 **덮어써야** 하며 기존 헤더에 추가하면 안 됩니다. 쉼표 체인·포트·주소 이외 값·누락은 400으로 거부합니다. IPv4 매핑 IPv6와 IPv6 표기를 정규화하여 한도 우회를 줄입니다. 분당 제한·일일 IP 보조 제한·사용량 조회에 같은 주소를 사용합니다.

CDN, 로드밸런서, 원격 프록시를 추가하는 구성은 이 템플릿의 범위 밖입니다. Nginx의 real-IP 설정을 임의 활성화하지 말고 실제 신뢰 경로부터 검증해야 합니다. 공용 IP의 여러 사용자는 IP 보조 상한을 공유합니다.

AI 요청 재전송을 막기 위해 프록시 자동 upstream 재시도를 끄고, 프록시 읽기 대기는 서버 최대 120초보다 긴 130초로 둡니다. [Nginx 공식 프록시 설정 문서](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

## 설치·배포 순서

1. Node.js 24 이상과 Nginx, TLS 인증서, 서비스 계정 및 영속 데이터 디렉터리를 준비합니다. 서버의 실제 경로·권한을 확인합니다.
2. 저장소 전체를 새 릴리스 디렉터리에 체크아웃합니다. 백엔드가 프론트엔드의 공유 Schema 코드를 가져오므로 backend만 복사하지 않습니다.
3. 프론트엔드에서 `npm ci --include=dev` 후 `npm run build`, 백엔드에서 `npm ci --include=dev`와 `npm run check`, `npm test`를 실행합니다. 현재 빌드 도구와 실행기는 devDependencies에 있으므로 제외하지 않습니다.
4. 서비스 관리자의 작업 디렉터리를 해당 릴리스의 `backend`로 지정합니다. 예시 실행 명령은 `node --env-file=/etc/sebit/backend.env --import tsx src/index.ts`입니다. 자동 시작·재시작·권한·로그 보관은 선택한 서비스 관리자에서 설정합니다. 백엔드는 한 프로세스만 실행합니다.
5. 백엔드 시작 후 로컬 `/api/health`를 확인합니다. `/api/usage`의 직접 점검에는 신뢰 프록시 계약에 맞는 단일 테스트 IP 헤더가 필요합니다. 실제 운영 검수는 HTTPS 프록시를 통해 진행합니다.
6. Nginx의 root를 같은 릴리스로 맞춘 후 **`nginx -t`가 통과할 때만** reload합니다. HTTPS 홈·사용량 조회·샘플 편집·ZIP을 점검합니다. 유료 AI 호출 검수는 샘플 요청으로 별도 수행합니다.

## 출시 전 확인

- 외부에서 3001이 접근되지 않고 `.env`, 데이터베이스, backend 파일이 다운로드되지 않는지 확인합니다.
- 서로 다른 두 클라이언트에서 분당/IP 한도가 분리되는지, 사용자가 넣은 X-Forwarded-For가 Nginx에서 교체되는지 확인합니다. HTTPS 쿠키의 Secure·HttpOnly·SameSite도 확인합니다.
- 허용하지 않은 Origin, 잘못된 프록시 헤더, 점검 모드 요청이 거부되는지 확인합니다. 서버 로그·DB에 본문과 키가 없는지 점검합니다.
- 디스크 여유 공간과 SQLite 백업, 인증서 갱신, 프로세스 종료/재시작, 로그 보관을 확인합니다. usage DB는 서명 비밀값도 포함하므로 보호된 백업이 필요합니다.

## 점검·백업·롤백

점검 시 `AI_MAINTENANCE=true`로 재시작하면 새 AI 호출은 거부하고 샘플·CMS·다운로드는 유지합니다. 재시작 전 진행 요청이 끝날 시간을 주며, 강제 종료한 요청은 사용량 예약 만료 후 반환됩니다.

초기 단일 서버의 백업은 백엔드를 중지한 상태에서 두 DB와 존재하는 SQLite 저널 파일을 함께 보호된 위치로 복사하고 재시작하는 방식으로 진행합니다. 실행 중인 DB 파일을 단순 복사하지 않습니다. 복원 검수는 서비스 중단 상태에서 별도로 수행합니다.

릴리스의 실패 시 백엔드를 중지하고 이전 코드·프론트엔드 경로로 되돌린 뒤 같은 영속 DB 경로로 재시작합니다. DB 구조 호환성을 먼저 확인하며 호환되지 않는다면 백업 복원이 필요할 수 있습니다. 사용량 DB를 과거 백업으로 복원하면 그 이후 사용량이 소실되는 점을 고려합니다. `nginx -t`, HTTPS health·사용량·샘플 흐름을 재확인합니다.

현재 SQLite 일일 한도는 동일 머신 파일 공유를 지원하지만 분당·동시성 제한은 프로세스 메모리입니다. 여러 프로세스/서버로 확장할 때는 공용 제한 저장소와 운영 인증 체계를 별도 구현해야 합니다. Nginx 설정은 아직 실제 Linux 환경에서 `nginx -t` 또는 HTTPS 통합 검증을 수행하지 않은 템플릿입니다.
